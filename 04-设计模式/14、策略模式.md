# 1、场景引入

电商结算支持多种促销：**满减**、**打折**、**无优惠**。促销规则经常变，且不希望 `OrderService` 里堆满 if-else。

# 2、普通写法

```java
public double checkout(String type, double price) {
    if ("full_reduction".equals(type)) {
        return price >= 200 ? price - 50 : price;
    } else if ("discount".equals(type)) {
        return price * 0.8;
    }
    return price;
}
```

**问题**：算法与上下文耦合；新增规则改核心逻辑；难以单独测试某种策略。

# 3、设计模式做法

## 介绍

策略模式（Strategy）：定义一系列算法，把它们**封装起来**，并使它们可以**相互替换**。策略模式让算法独立于使用它的客户端而变化。

## 两种常见写法

GoF 教科书和实际业务都属策略模式，差别在**谁、怎么选策略**。

| | 写法一：显式 set（笔记基础示例） | 写法二：support + 策略集合（业务更常见） |
| :--- | :--- | :--- |
| 谁选策略 | 客户端 / 上下文外部 `setStrategy(...)` | 上下文根据类型从集合里**自动找** |
| 策略接口 | 只有业务方法，如 `calc()` | 多一个 `support(type)` 表示「我能不能处理」 |
| 典型场景 | 调用方已知用哪种算法 | 调用方只传类型，由框架挑实现（支付渠道、导出格式等） |

### 写法一：显式指定策略（GoF 经典）

```java
// 策略接口：封装促销算法
public interface PromotionStrategy {
    double calc(double price);
}

// 具体策略：满减
public class FullReductionStrategy implements PromotionStrategy {
    public double calc(double price) {
        return price >= 200 ? price - 50 : price;
    }
}

// 具体策略：打折
public class DiscountStrategy implements PromotionStrategy {
    public double calc(double price) {
        return price * 0.8;
    }
}

// 上下文：持有「当前」策略，外部 set 进来
public class OrderContext {
    private PromotionStrategy strategy;

    public void setStrategy(PromotionStrategy strategy) {
        this.strategy = strategy;
    }

    public double checkout(double price) {
        return strategy.calc(price);
    }
}
```

### 写法二：support + 策略集合

```java
public interface PayStrategy {
    boolean support(String payType);  // 是否支持该支付类型
    void pay(Order order);
}

public class WechatPayStrategy implements PayStrategy {
    public boolean support(String payType) { return "wechat".equals(payType); }
    public void pay(Order order) { /* 微信支付 */ }
}

public class AlipayStrategy implements PayStrategy {
    public boolean support(String payType) { return "alipay".equals(payType); }
    public void pay(Order order) { /* 支付宝 */ }
}

// 上下文：注入所有实现，按类型自动选策略（Spring 常 @Autowired List<PayStrategy>）
public class PayContext {
    private final List<PayStrategy> strategies;

    public PayContext(List<PayStrategy> strategies) {
        this.strategies = strategies;
    }

    public void checkout(String payType, Order order) {
        for (PayStrategy s : strategies) {
            if (s.support(payType)) {
                s.pay(order);
                return;
            }
        }
        throw new IllegalArgumentException("unsupported payType: " + payType);
    }
}
```

> **本质没变**：仍是「多种算法封装成实现类 + 上下文委托执行」。  
> `support + 集合` 只是**选型方式**，不是另一种设计模式；也不是工厂（工厂侧重创建对象，这里是选谁执行业务）。

## 客户端调用

```java
public class Client {
    public static void main(String[] args) {
        // 写法一：显式 set
        OrderContext ctx = new OrderContext();
        ctx.setStrategy(new FullReductionStrategy());
        System.out.println(ctx.checkout(300));

        // 写法二：只传类型，上下文内部 match
        PayContext payCtx = new PayContext(List.of(new WechatPayStrategy(), new AlipayStrategy()));
        payCtx.checkout("wechat", new Order());
    }
}
```

## 注意事项

1. 写法一：客户端或上层代码**明确知道**用哪种策略时更清晰。
2. 写法二：策略种类多、常扩展（加实现类即可），适合 Spring 注入 `List<Strategy>`；注意多个 `support` 同时命中时的优先级。
3. 与模板方法：策略是**组合+接口**换整个算法；模板方法是**继承**固定流程换部分步骤。
4. 与状态模式：策略是「选用哪种算法」；状态是「对象当前处于什么状态，行为随之变」。
