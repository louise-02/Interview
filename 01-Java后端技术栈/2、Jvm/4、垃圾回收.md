# 4、垃圾回收

## 1、为什么需要 GC

Java 堆上对象由 GC **自动回收**，程序员无需（也无法）对普通对象显式 `free`。GC 核心问题：

1. **哪些内存需要回收？**
2. **什么时候回收？**
3. **如何回收？**

## 2、判断对象是否存活

### 2.1 引用计数法

对象被引用则计数 +1，为 0 则回收。**Java 不采用**——无法解决**循环引用**。

### 2.2 可达性分析（Java 采用）

从 **GC Roots** 出发，不可达的对象可被回收。

**GC Roots 包括（典型）**

- 虚拟机栈中引用的对象（局部变量、参数）
- 方法区中 static 属性引用的对象
- 方法区中常量引用的对象
- 本地方法栈中 JNI 引用的对象
- JVM 内部引用（基本类型 Class、系统类加载器等）
- 同步锁持有的对象
- JMX / JNI 等临时引用

### 2.3 finalize()

对象在可达性分析后**第一次**标记时，若类重写了 `finalize()` 且尚未执行过，会放入 F-Queue，由低优先级 Finalizer 线程执行。

- 在 `finalize()` 中**重新建立引用**（如 `this` 赋给静态变量），对象可**复活**（第二次标记时移除）。
- **不推荐依赖** finalize；JDK 9 起 `Object.finalize()` 已 deprecated，用 `Cleaner` / `try-with-resources` 替代。

## 3、引用类型

| 类型 | 回收时机 | 典型用途 |
| ---- | -------- | -------- |
| **强引用** | 不回收，OOM 也不回收 | `Object o = new Object()` |
| **软引用** SoftReference | 内存不足前回收 | 缓存 |
| **弱引用** WeakReference | 下次 GC 即回收 | ThreadLocal Map 的 key、WeakHashMap |
| **虚引用** PhantomReference | 无法通过引用取对象，仅跟踪回收 | 堆外内存回收跟踪、Cleaner |

引用队列 `ReferenceQueue`：对象被回收前，引用会入队，便于清理关联资源。

## 4、垃圾回收算法

| 算法 | 思路 | 优点 | 缺点 |
| ---- | ---- | ---- | ---- |
| **标记-清除** | 标记存活 → 清除未标记 | 实现简单 | 碎片、两次扫描 |
| **标记-复制** | 存活对象复制到另一块，清空原区 | 无碎片、适合新生代 | 浪费一半空间（Survivor 折中） |
| **标记-整理** | 标记存活 → 向一端移动 → 清理边界外 | 无碎片 | 移动对象成本高，适合老年代 |

**分代假说**

1. 绝大多数对象**朝生夕灭**。
2. 熬过多次 GC 的对象**难以消亡**。

因此：**新生代**用复制；**老年代**用标记-清除或标记-整理。

## 5、Minor GC、Major GC、Full GC

| 名称 | 范围 | 触发（典型） |
| ---- | ---- | ------------ |
| **Minor GC / Young GC** | 年轻代 | Eden 满 |
| **Major GC** | 老年代 | 老年代空间不足 |
| **Full GC** | 整堆 + 方法区/元空间等 | 老年代满、Metaspace 不足、`System.gc()`、CMS 失败等 |

**Stop-The-World（STW）**：GC 时暂停所有应用线程。调优目标之一是**缩短 STW** 与 **Full GC 频率**。

**安全点（Safepoint）**：线程可安全暂停、开始 GC 的位置（方法调用、循环回边等）。**安全区域**用于 Native 线程长时间 idle。

## 6、垃圾收集器概览

```
新生代                    老年代
Serial  ────────────────  Serial Old
ParNew  ────────────────  CMS
Parallel Scavenge ─────── Parallel Old
        G1（整堆 Region，逻辑分代）
        ZGC / Shenandoah（低延迟，JDK 版本相关）
```

### 6.1 Serial / Serial Old

单线程，STW。Client 模式或堆很小（几十 MB）时可用。

### 6.2 ParNew

Serial 的多线程版，常与 **CMS** 搭配（CMS 只负责老年代，年轻代需 ParNew 等）。

### 6.3 Parallel Scavenge + Parallel Old

**吞吐量优先**，JDK 8 默认（Server）。参数：`-XX:MaxGCPauseMillis`、`-XX:GCTimeRatio`。

### 6.4 CMS（Concurrent Mark Sweep）

**低延迟**，老年代并发标记-清除。

阶段：初始标记（STW）→ 并发标记 → 重新标记（STW）→ 并发清除。

缺点：碎片、CPU 敏感、并发阶段占资源；**浮动垃圾**；Concurrent Mode Failure 退化为 Serial Old Full GC。

JDK 9 起 deprecated，**JDK 14 移除**。

### 6.5 G1（Garbage First）

JDK 9+ **默认**。整堆划分为多个 **Region**（1~32MB），每个 Region 可扮演 Eden / Survivor / Old / Humongous（大对象）。

特点：

- 可预测停顿：`-XX:MaxGCPauseMillis=200`
- 优先回收垃圾最多的 Region（Garbage First）
- 整体标记-整理 + 局部复制

常用参数：

```bash
-XX:+UseG1GC
-XX:MaxGCPauseMillis=200
-XX:G1HeapRegionSize=16m
```

### 6.6 ZGC / Shenandoah

**超低延迟**（毫秒级 STW），适合大堆（TB 级）。并发整理，**读屏障 / 着色指针**等技术。

**ZGC 要点**

- **着色指针（Colored Pointer）**：在 64 位指针 unused bits 存 GC 元数据，压缩后仍支持多 TB 堆。
- **并发标记 + 并发整理**，STW 主要在初始标记、再标记等短阶段。
- **JDK 11** 实验，**JDK 15+** 生产可用；**JDK 21** 起**分代 ZGC**（`-XX:+ZGenerational`）。
- 参数：`-XX:+UseZGC`，`-Xmx` 设堆，无固定年轻代比例（非分代模式下）。

**Shenandoah**

- OpenJDK Red Hat 等贡献，**Brooks Pointer** + 并发 evacuation。
- `-XX:+UseShenandoahGC`（视 JDK 发行版是否内置）。

### 6.7 G1 工作流程（详）

```
Young GC（Evacuation）
  → Eden + Survivor 存活对象复制到空 Region

并发标记周期（Mixed GC 的前奏）
  1. 初始标记（STW，通常很短，可搭 Young GC）
  2. 并发标记（根扫描 + 全堆可达性）
  3. 最终标记（STW，处理 SATB 写屏障遗留）
  4. 筛选回收（STW，选收益高的 Region）

Mixed GC
  → 回收部分 Old Region + 全部 Young，控制停顿目标
```

**Humongous 对象**：超过 Region 一半的对象占连续 **Humongous Region**，不参与正常复制，回收依赖 Full GC 或 Mixed GC。

**Remembered Set（RSet）**：每个 Region 记录**谁引用了我**，避免 Minor/Mixed 时扫描整堆 Old。

**SATB 写屏障**：并发标记期间，记录引用变更，保证不丢存活对象。

**常用 G1 参数**

```bash
-XX:+UseG1GC
-XX:MaxGCPauseMillis=200
-XX:G1HeapRegionSize=16m
-XX:InitiatingHeapOccupancyPercent=45   # 并发标记触发阈值
-XX:G1MixedGCCountTarget=8
-XX:G1OldCSetRegionThresholdPercent=10  # Mixed GC 选 Old Region 比例
```

### 6.8 卡表与写屏障（分代 GC 基础）

**跨代引用**：Minor GC 只扫 Young，但 Young 可能被 Old 引用 → 需 **Remembered Set / 卡表（Card Table）**。

- 老年代划分为 **512 字节卡页**，卡表标记哪些卡页有指向 Young 的引用。
- **写屏障**：引用赋值时更新卡表（Minor GC 只扫 dirty card）。

CMS、Parallel、G1 实现细节不同，思想一致：**避免 Full 扫描 Old**。

### 6.9 Epsilon GC

无回收，分配至 OOM。基准测试、极短任务。见第 11 章。

## 7、GC 日志（JDK 8 / 11+）

**JDK 8**

```bash
-XX:+PrintGCDetails -XX:+PrintGCDateStamps -Xloggc:/path/gc.log
```

**JDK 9+ 统一日志**

```bash
-Xlog:gc*:file=/path/gc.log:time,uptime,level,tags
```

关注：**GC 类型**、**停顿时间**、**回收前后堆占用**、**Full GC 频率**、**Metaspace**。

## 8、内存分配与晋升策略

1. 新对象优先 **Eden**（TLAB 无锁分配，见第 2 章）。
2. **大对象**可能直接进 **Old**（`-XX:PretenureSizeThreshold`，Parallel；G1 为 **Humongous Region**，约为 RegionSize 一半）。
3. **长期存活**：年龄计数在 Survivor 间复制，达 `-XX:MaxTenuringThreshold`（默认 15，最大 15）晋升 Old。
4. **动态年龄判定**：Survivor 中相同年龄对象大小超过 Survivor 一半，≥ 该年龄的对象直接晋升。
5. **分配担保（HandlePromotionFailure）**：Minor GC 前检查 Old 是否容纳 Survivor 所有存活；JDK 6 Update 24 后担保策略简化，仍可能因 Old 不足触发 **Full GC**。

## 9、Safepoint 与安全区域

- **Safepoint**：线程可安全暂停的点（方法调用、循环回边、异常跳转）。GC、dump、JIT 编译可能需 STW 到 Safepoint。
- **长时间 counted 循环**可能延迟进入 Safepoint → GC 停顿变长。
- **安全区域**：线程 Sleep/Blocked 无法响应 Safepoint 时，标记进入安全区域；离开时再检查 GC 是否完成。

## 10、常见面试题

**1. 什么时候会 Full GC？**

老年代不足、元空间不足、System.gc（`-XX:+DisableExplicitGC` 可禁）、CMS 失败、担保失败等。

**2. 四种引用区别？**

见上表；WeakReference 用于避免内存泄漏（如 ThreadLocal 弱 key）。

**3. G1 和 CMS 区别？**

G1 基于 Region、可预测停顿、整堆管理；CMS 仅老年代、标记-清除易碎片、已移除。

**4. 如何减少 Full GC？**

合理堆大小、减少大对象与长期存活对象、避免 Metaspace 泄漏、选合适收集器、排查内存泄漏。

**5. G1 Mixed GC 是什么？**

并发标记后，在满足停顿目标下回收部分 Old Region + Young，避免一次性 Full GC。

**6. CMS 浮动垃圾是什么？**

并发清除阶段应用仍在产生垃圾，只能下次 GC 处理；可能导致 Concurrent Mode Failure。
